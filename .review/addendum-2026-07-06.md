### CONTEXT

- Codebase: ghqctoolkit — a QC-management system for data-analysis workflows
  that uses **GitHub Issues as its datastore**: QC state is serialized into and
  re-parsed from issue bodies/comments. Hybrid: Rust interactive CLI + Axum
  HTTP API + embedded React web UI over a shared Rust library core (~33k LOC
  Rust, ~12.5k LOC TS). Version 0.7.1, ~84 commits, actively developed.
- Primary consumers: scientists, internal and external — non-developer users
  for whom the QC record's *trustworthiness* is the product. **Shared
  multi-user hosts (Posit Workbench) are the typical deployment**; personal
  machines are supported but secondary `[Q2]`.
- Known constraints or intentional decisions worth flagging up front: no
  database by design (GitHub is the source of truth); issue bodies/comments
  **are hand-edited in the field and old-ghqc-format issues are still live** —
  parsers must be robust to both `[Q5]`; configuration (checklists, logo,
  options) comes from a separate cloned git repo; review auto-stash is one-way
  by design. The gix→git-CLI migration is intended to complete: **pure git-CLI
  is the end state and remaining gix usage can be dropped** `[Q10]`.
- Areas of specific concern: correctness of QC-state reconstruction from GitHub
  text (the parsers), CLI↔API behavioral divergence, and network exposure of
  the unauthenticated local server — the all-interfaces bind was a workaround
  for one client's broken localhost loopback, since mitigated elsewhere, so a
  loopback default is now achievable `[Q1]`. Correctness outranks API
  responsiveness, but not at responsiveness's total expense `[Q9]`.

**T1 — Issue-body grammar: unversioned serialization contract, ~5 writers, ≥2
drifted parsers (survey H1; confidence high).**
QC state round-trips through literal markdown patterns (`initial qc commit:`,
`current commit:`, `approved qc commit:`, `comparing commit:`, `git branch:`,
`# QC Review`, `# QC Un-Approval`, `## Relevant Files` + `### Gating QC` /
`### Previous QC`, `## File History`). Writers: `src/create.rs:39-40`,
`src/comment.rs:24`, `src/approve.rs:32,73`, `src/review.rs:43-51`,
`src/relevant_files.rs:114-121,171`. Parsers: `src/issue.rs:329-508,543-606`
and an independent second implementation in
`src/api/types/responses.rs:643-723`; `src/record/typst.rs` re-parses comment
markdown a third way. Known drift: `responses.rs:650-664` branch parser misses
HTML `<a>` links that `issue.rs:401-435` handles (HTML-link bodies occur —
`issue.rs:1561`); `responses.rs:687-692` reads `### Relevant QC`/`### Relevant
File` sections that `issue.rs:444` does not — the *rule* (only Gating/Previous
QC block approval) is intentional, and the maintainer endorses collapsing to
one shared parser that parses everything and lets callers use what they need
`[Q6]`. The maintainer confirms bodies/comments **are hand-edited on GitHub
and old-ghqc-format issues are still live**, so parser robustness against both
is a requirement, not a nice-to-have `[Q5]`. Investigate: enumerate the
full grammar; build a writer→parser matrix; run the same body corpus (HTML
links, multi-part bodies from `src/body_splitter.rs`, hand-edited and
old-version bodies) through both parsers and diff; probe false-positive
state from comments *quoting* patterns (e.g. a quoted `approved qc commit:`);
probe short-SHA (≥7 char) prefix-match collisions (`issue.rs:216-227`) and the
comment-ordering dependence of approval/unapproval (`issue.rs:337-382`).

#### Purpose and type

`ghqc` is a Quality Control management system for data-analysis workflows
(pharma/scientific users): each file under QC gets a GitHub Issue, issues are
grouped into Milestones, and the full QC lifecycle (create → review → comment →
approve → record PDF → archive) is driven through the tool. GitHub Issues are
the **system of record** — QC state is serialized into and re-parsed from issue
bodies and comments. It is a hybrid: a Rust interactive CLI + an Axum HTTP API
+ an embedded React web UI, all over a shared Rust library core. ~33k LOC Rust,
~12.5k LOC TypeScript.

#### Entry points

- **Binary** `ghqc` — `src/main.rs:394` (`#[tokio::main]`, feature `cli`).
  Clap subcommands: `issue {create,comment,approve,unapprove,review,status,rename}`,
  `milestone {status,record,archive}`, `configuration {setup,status}`,
  `cache {status,dir,remove}`, `auth {login,logout,status,token}`, `sitrep`,
  `serve` (feature `api` without `ui`, `main.rs:1193`), `ui` (feature `ui`,
  `main.rs:1224`).
- **HTTP routes** — all registered in `create_router`, `src/api/server.rs:43-132`:
  31 routes under `/api/*` (milestones, issues, comments/approve/unapprove/review,
  files tree/content/raw/collaborators, previews, record upload/preview/generate,
  archive generate, configuration, assignees, repo, commits, health). Documented
  path-for-path in `openapi/openapi.yml` (hand-maintained per `AGENTS.md`).
- **UI server** — `ghqctoolkit::ui::run` (`src/ui/mod.rs`) serves the rust-embed
  SPA (`ui/dist/client/`) plus the same API router; binds via
  `bind_local_server` (`src/api/server.rs:138-177`).
- **No background workers or scheduled tasks.** The frontend polls
  `GET /api/repo` on an interval (default 15 s, `ui/src/api/repo.ts:47-55`),
  pausing after 5 min of user inactivity.

#### Intended layering

Inferred from `src/lib.rs` (domain modules private, re-exported; `cli`/`api`/`ui`
feature-gated) and the trait-generic handlers: **CLI and API are peer frontends
over a shared core library + git layer**. In practice both frontends carry
substantial orchestration and validation of their own (see PRIORITY TARGETS T2),
and `main.rs` itself is a third place where orchestration lives.

#### Most load-bearing

1. `src/git/mod.rs` + `src/git/provider.rs` (`GitInfo`/`GitProvider`) — every CLI
   command and every API request path constructs or traverses it.
2. `src/issue.rs` (`IssueThread`) — all status, approve, record, and archive flows
   depend on its reconstruction of QC state from GitHub text.
3. The pair `src/cli/context.rs` ↔ `src/api/routes/*` — the two parallel
   orchestration/validation layers through which every user action flows.
