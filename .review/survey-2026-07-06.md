## 1. Repository map

### Purpose and type

`ghqc` is a Quality Control management system for data-analysis workflows
(pharma/scientific users): each file under QC gets a GitHub Issue, issues are
grouped into Milestones, and the full QC lifecycle (create → review → comment →
approve → record PDF → archive) is driven through the tool. GitHub Issues are
the **system of record** — QC state is serialized into and re-parsed from issue
bodies and comments. It is a hybrid: a Rust interactive CLI + an Axum HTTP API
+ an embedded React web UI, all over a shared Rust library core. ~33k LOC Rust,
~12.5k LOC TypeScript.

### Entry points

- **Binary** `ghqc` — `src/main.rs:394` (`#[tokio::main]`, feature `cli`).
  Clap subcommands: `issue {create,comment,approve,unapprove,review,status,rename}`,
  `milestone {status,record,archive}`, `configuration {setup,status}`,
  `cache {status,dir,remove}`, `auth {login,logout,status,token}`, `sitrep`,
  `serve` (feature `api` without `ui`, `main.rs:1193`), `ui` (feature `ui`,
  `main.rs:1224`).
- **HTTP routes** — all registered in `create_router`, `src/api/server.rs:43-132`:
  31 routes under `/api/*` (milestones, issues, comments/approve/unapprove/review,
  files tree/content/raw/collaborators, previews, record upload/preview/generate,
  archive generate, configuration, assignees, repo, commits, health). Documented
  path-for-path in `openapi/openapi.yml` (hand-maintained per `AGENTS.md`).
- **UI server** — `ghqctoolkit::ui::run` (`src/ui/mod.rs`) serves the rust-embed
  SPA (`ui/dist/client/`) plus the same API router; binds via
  `bind_local_server` (`src/api/server.rs:138-177`).
- **No background workers or scheduled tasks.** The frontend polls
  `GET /api/repo` on an interval (default 15 s, `ui/src/api/repo.ts:47-55`),
  pausing after 5 min of user inactivity.

### Intended layering

Inferred from `src/lib.rs` (domain modules private, re-exported; `cli`/`api`/`ui`
feature-gated) and the trait-generic handlers: **CLI and API are peer frontends
over a shared core library + git layer**. In practice both frontends carry
substantial orchestration and validation of their own (see hypotheses 2), and
`main.rs` itself is a third place where orchestration lives.

### Most load-bearing

1. `src/git/mod.rs` + `src/git/provider.rs` (`GitInfo`/`GitProvider`) — every CLI
   command and every API request path constructs or traverses it.
2. `src/issue.rs` (`IssueThread`) — all status, approve, record, and archive flows
   depend on its reconstruction of QC state from GitHub text.
3. The pair `src/cli/context.rs` ↔ `src/api/routes/*` — the two parallel
   orchestration/validation layers through which every user action flows.

### Cross-cutting concerns

- **Errors**: ~15-17 per-module `thiserror` enums (no crate-wide type). CLI:
  anyhow in `main.rs`. API: everything funnels into `ApiError`
  (`src/api/error.rs:12`) via seven `From` impls that all call `.to_string()`
  (`error.rs:64-115`); status mapping is coarse (all `GitInfoError`/`IssueError`/
  etc. → 500; all `GitHubApiError` → 502) with ~50 ad-hoc `map_err` closures in
  handlers compensating. Some enum variants drop the source (e.g.
  `GitInfoError::RepoOpen`, `src/git/mod.rs:38-41`).
- **Config**: `determine_config_dir` (`src/configuration.rs:459-511`; precedence
  `--config-dir` → `GHQC_CONFIG_REPO` → `GHQC_CONFIG_DIR` → XDG default) +
  `Configuration::from_path` + `load_checklists` — the sequence is re-composed at
  ~8 call sites (`main.rs:432-434, 799-800, 1121, 1138-1140, 1197-1199, 1239-1241`;
  `cli/sitrep.rs:160,416`; `api/routes/configuration.rs:90-91`). `options.yaml`
  read failures silently fall back to defaults (`configuration.rs:130`).
- **Env reads**: mockable `EnvProvider` trait (`src/utils.rs:6-24`) plus four raw
  `std::env::var` bypasses (`cache.rs:201`, `main.rs:1110`, `cli/cache.rs:168`,
  `api/routes/configuration.rs:33`). Cache TTL default (3600 s) is defined in
  `cache.rs:200-206` and restated as a hardcoded string in `cli/cache.rs:167-172`.
- **Auth**: `AuthStore` (ghqc's encrypted store) feeding `AuthSources`
  (`src/git/auth.rs:44-82`, 6-source priority). Config-repo `GitInfo` is built
  with `auth_store: None` at 5 sites (`main.rs:1141,1200,1242`;
  `cli/sitrep.rs:422`; `cli/cache.rs:223`). Git shell-outs (`GitCommand`
  clone/fetch, `action.rs:113-178`) use ambient git credential helpers, **not**
  `AuthSources` — two independent auth paths for network operations.
- **Logging**: `env_logger` scoped to `ghqctoolkit` + `octocrab` (`main.rs:398-402`);
  API request-line middleware (`server.rs:21-29`) + `TraceLayer`.
- **Validation**: no single boundary — duplicated per frontend (see hypothesis 2).
- **Concurrency**: axum/tokio; `AppState` holds `Arc<G>` + tokio `RwLock<Configuration>`;
  no shared mutable domain state; fresh gix repo per call for thread safety
  (`git/mod.rs:138`). `spawn_blocking` used in most handlers but not all
  (`api/routes/commits.rs:63,86`; `api/routes/comments.rs:174`;
  `api/fetch_helpers.rs:89,97` run subprocess/gix work inline).
- **Server exposure**: listener binds `Ipv6Addr::UNSPECIFIED`/`Ipv4Addr::UNSPECIFIED`
  (all interfaces, `server.rs:171-177`) while docs and printed URL say loopback
  (`docs/serve.md:25-26`); wildcard CORS with a "local development only" comment
  (`server.rs:35-41`); no authentication on any API route.

### Build / test / CI shape

Cargo features `cli` / `api` / `ui` (`ui` ⇒ `api`); `build.rs` runs
`bun install && bun run build` when `ui` is enabled and the SPA embeds via
rust-embed. Tests: 307 in-module `#[test]`s (heaviest: issue.rs 59,
record/typst.rs 31, approve.rs 24, create.rs 23) + a YAML-driven API harness
(57 cases, `src/api/tests/`) that exercises real axum routing against a fully
mocked `MockGitInfo`; Playwright E2E in `ui/tests/` runs against a mocked
backend. CI (`.github/workflows/ci.yml`) runs fmt + `cargo test/check
--features cli,api` on 3 OSes only — no clippy, no other feature combos; the
`ui` feature combo is first compiled at release time (`release.yml`);
`ui-tests.yml` is path-filtered to `ui/**` so backend changes never trigger it.
`lefthook.yml` pre-commit runs `cargo check/test --all` at **default features**,
differing from CI.

## 2. Risk hypotheses (ranked)

### H1 — The issue-body markdown grammar is an unversioned serialization contract with ~5 writers and ≥2 already-drifted parsers

- **Hypothesis**: QC state round-trips through an informal markdown grammar
  (`initial qc commit:`, `current commit:`, `approved qc commit:`,
  `comparing commit:`, `git branch:`, `# QC Review`, `# QC Un-Approval`,
  `## Relevant Files`/`### Gating QC`/`### Previous QC`, `## File History`)
  whose writers and parsers are scattered and have no shared definition or
  version marker; the two parser implementations have drifted and will drift
  further.
- **Signal**: Writers: `create.rs:39-40`, `comment.rs:24`, `approve.rs:32,73`,
  `review.rs:43-51`, `relevant_files.rs:114-121,171`. Parsers:
  `issue.rs:329-508,543-606` and an independent second implementation in
  `api/types/responses.rs:643-723`. Concrete drift: `parse_branch_from_body_simple`
  (`responses.rs:650-664`) handles markdown links only, while
  `parse_branch_from_body` (`issue.rs:401-435`) also handles HTML `<a href>`
  links — and tests show HTML-link bodies exist in the wild (`issue.rs:1561`).
  `parse_blocking_qcs` (`issue.rs:444`) knows `### Gating QC`/`### Previous QC`;
  `parse_relevant_file_infos` (`responses.rs:687-692`) additionally handles
  `### Relevant QC` and `### Relevant File`. `record/typst.rs` re-parses comment
  markdown a third way for PDF rendering. `body_splitter.rs` writes multi-part
  bodies/comments that all parsers must tolerate. Approval/unapproval semantics
  depend on comment *ordering* and prefix-matching short SHAs ≥7 chars
  (`issue.rs:216-227,337-382`).
- **If true, cost**: silent QC-state misreads — wrong branch resolution, missed
  blocking QCs, wrong approved commit — corrupting the audit record that is the
  product's entire value proposition; every new body feature requires
  synchronized edits in N files with no compile-time linkage.
- **Investigation sketch**: enumerate the full grammar (grep the literal
  patterns above); build a writer→parser matrix; feed the same body corpus
  (HTML links, split bodies, hand-edited bodies, old-version bodies, GH-rewritten
  links) through both `issue.rs` and `responses.rs` parsers and diff results;
  check what happens when a *comment quotes* another comment containing
  `approved qc commit:` (false approval?); check short-SHA prefix collision
  behavior; assess whether a hidden HTML marker / structured block could anchor
  the grammar.
- **Confidence**: high.

### H2 — CLI and API are divergent re-implementations of the same operations, with validation drift and shared-core bypasses

- **Hypothesis**: For most operations the API does not call the core
  orchestration functions the CLI uses; validation rules differ per frontend,
  so the same user action can produce different QC records depending on
  interface.
- **Signal**: API `approve_issue` (`api/routes/comments.rs:54-124`) re-implements
  blocking-QC validation instead of calling `approve_with_validation`
  (`approve.rs:213`); core treats `close_issue` failure as fatal
  (`approve.rs:245`) while the API ignores it (`comments.rs:101` `.is_ok()`) —
  a silently approved-but-open issue. `unapprove_issue` (`comments.rs:127-149`)
  bypasses `unapprove_with_impact` (`approve.rs:499`). Commit validation: CLI
  requires membership in the file's commit history
  (`cli/context.rs:429-463,641-651,877-929`); API only hex-parses
  (`comments.rs:182-186`). Assignees: CLI warn+drop (`context.rs:62-76`) vs API
  400 (`api/routes/issues.rs:98-117`). Milestone: CLI auto-creates
  (`context.rs:44-52`) vs API 404s (`issues.rs:41-51`). Dependency-cycle checks
  exist only on the API path (`create.rs:660-670`). Rename orchestration is
  duplicated near-verbatim (`cli/rename.rs:14-36,239-296` vs
  `api/routes/issues.rs:412-511`). Blocking-QC status rollup implemented twice
  (`qc_status.rs:434` vs `issues.rs:301-356`). The `serve`/`ui` arms of main.rs
  (`1193-1223` vs `1224-1261`) are copy-paste duplicates of each other.
- **If true, cost**: a fix or rule change lands on one side only; the QC record's
  integrity guarantees differ by frontend (e.g. the UI can approve at a commit
  that never touched the file); doubled maintenance on every feature.
- **Investigation sketch**: build a per-operation contract table
  (create/comment/review/approve/unapprove/rename/status) listing validation,
  defaulting, and failure semantics for each side; confirm each divergence by
  reading both paths; identify which belong in the core (`QCApprove` et al.) as
  the single boundary; verify the approve-close-failure divergence with a test.
- **Confidence**: high.

### H3 — The unauthenticated API binds all interfaces on shared multi-user hosts

- **Hypothesis**: `ghqc ui`/`serve` listens on `0.0.0.0`/`[::]` with no
  authentication and wildcard CORS, while its primary deployment target
  includes shared Posit Workbench servers — so any user or network peer able to
  reach the port can act with the owner's GitHub token (post comments, approve,
  close issues), read any file in the repo (`/api/files/raw`, `/api/files/content`),
  and write files to disk (`/api/record/generate`, `/api/archive/generate`
  output paths).
- **Signal**: `bind_ipv4`/`bind_dual_stack_ipv6` use `UNSPECIFIED`
  (`api/server.rs:171-177`); CORS `Any` with an explicit "local development
  only, NOT for production" comment (`server.rs:35-41`); no auth middleware in
  `create_router`; `docs/serve.md:25-26` describes the printed URL as "a literal
  loopback URL" — the docs assume loopback semantics the bind doesn't provide;
  Posit Workbench deployment is a first-class concern
  (`.ai/docs/posit-workbench-proxy.md`).
- **If true, cost**: cross-user GitHub actions under the victim's identity on
  shared hosts; falsified QC records (the thing the tool exists to make
  trustworthy); repo content disclosure.
- **Investigation sketch**: confirm whether the Workbench proxy requires a
  non-loopback bind (typically it proxies to localhost — check); test that path
  traversal guards on `/api/files/*` hold (`api/tests/cases/files/*path_traversal*`
  exist) and audit archive/record `output_path` handling
  (`api/routes/archive.rs:34-75`, `record.rs:245-257`) for writes outside the
  repo; sketch loopback-by-default + `--host` opt-in and/or a bearer token baked
  into the launched URL.
- **Confidence**: high on the facts; medium on real-world exploitability
  (depends on deployment norms — see Q1).

### H4 — Error structure is destroyed exactly at the API boundary that needs it

- **Hypothesis**: the per-module error enums carry useful variants, but every
  path into HTTP stringifies them, so status codes are wrong (user errors as
  500s, upstream 404s as 502s) and the UI can only display raw strings —
  driving the ~50 ad-hoc per-handler `map_err` closures as compensation.
- **Signal**: all seven `From` impls in `api/error.rs:64-115` call
  `err.to_string()`; `IssueError::MilestoneNotFound` → 500; every
  `GitHubApiError` → 502 regardless of upstream status; only `ApprovalError`
  gets variant-aware mapping (`error.rs:88-97`); handler-local overrides at e.g.
  `api/routes/archive.rs:47-136`, `configuration.rs:74-87`, `preview.rs:159-246`.
  Context loss also inside the library: variants wrapping causes without
  `#[source]` (e.g. `GitInfoError::RepoOpen`, `git/mod.rs:38-41`).
- **If true, cost**: misleading statuses train users (and the UI's error
  displays) to ignore errors; every new route re-invents mapping; debugging
  loses the cause chain.
- **Investigation sketch**: catalogue variant→status for each error enum;
  identify which handler-local `map_err` closures exist purely to fix the
  default mapping; sketch a single `IntoResponse` mapping that preserves
  variants (and a machine-readable error code field for the UI).
- **Confidence**: high (facts verified); medium that it ranks top-5 by cost.

### H5 — Cache correctness rests on documentation-level invalidation, not mechanism

- **Hypothesis**: the disk cache stores derived git facts (per-commit
  file-change records) with no schema/semantic version, so behavior changes in
  the producing code silently coexist with stale cached results until a human
  clears the cache.
- **Signal**: v0.7.0 changelog "Action Required: clear the commit cache…cached
  results from prior versions will still reflect the old behavior"
  (`CHANGELOG.md:6-9`); `docs/cache.md:108-112` documents manual clearing after
  upgrades as the normal procedure; no version stamp in `DiskCache`
  (`cache.rs:95-105`); cache-policy logic interleaved with git plumbing in
  `file_ops.rs:474-768` (`find_commits`, `get_commits_robust`,
  `find_or_cache_file_changes`).
- **If true, cost**: wrong QC statuses (file-changed flags drive
  `ChangesAfterApproval`) for users who don't read changelogs — silent, and in
  the direction of *false confidence* in QC state.
- **Investigation sketch**: check what keys/contents `CachedCommit` records and
  what would have to change to invalidate them; assess a `CACHE_SCHEMA_VERSION`
  (or binary-version) stamp; audit `get_commits_robust` fallback branches
  (`file_ops.rs:609-708`) for cases where cached and fresh data mix
  (`find_commits` validation, `file_ops.rs:557-594`).
- **Confidence**: medium-high.

### H6 — Record/PDF pipeline has broken temp-dir lifecycle on the API path

- **Hypothesis**: the Typst render path constructs its package-cache directory
  from a `TempDir` that is dropped (and its directory deleted) within the same
  expression, so every API-initiated render (which passes `cache: None`) hands
  Typst a nonexistent cache path; upload/preview temp files additionally leak.
- **Signal**: `render.rs:338-340` — `cache.map(...).unwrap_or(tempdir()?.path().to_path_buf())`
  (verified: the `TempDir` temporary is dropped at end of statement);
  `api/routes/record.rs:163` passes `None` cache to `render` while the CLI
  passes the disk cache (`main.rs:925`); uploads to `$TMPDIR/ghqc-uploads/<uuid>.pdf`
  are never deleted (`record.rs:70-78`); previews orphaned if never fetched
  (`record.rs:183,218`).
- **If true, cost**: Typst package downloads fail or re-download every render
  from the UI (the primary record-generation surface); tmp litter on shared
  hosts.
- **Investigation sketch**: trace `TypstWorld`'s use of `cache_dir`
  (`record/typst.rs`) — does it create the dir, and what fails when it's
  missing?; reproduce a UI-initiated record generation with a checklist that
  needs a Typst package; decide correct lifetime (hold the `TempDir` for the
  render's duration).
- **Confidence**: high the code is as described; medium on user-visible failure.

### H7 — Blocking git subprocesses and gix scans run inline on the async runtime in the hottest read paths

- **Hypothesis**: batch status reconstruction — the UI's most frequent
  operation — performs many `git log` subprocesses and gix worktree scans
  directly on tokio workers, stalling all concurrent requests; `spawn_blocking`
  usage elsewhere shows the intended policy isn't enforced.
- **Signal**: `api/fetch_helpers.rs:89,97` (`IssueThread::from_issue_comments`
  → `get_commits_robust`/`find_or_cache_file_changes` subprocesses; `dirty()`
  gix scan) inline in async `create_threads`; `api/routes/commits.rs:63,86`;
  `api/routes/comments.rs:174` (stash) and the diff-body generation inside
  `post_comment` (`git/api/write.rs:189`); contrast with correct wrapping at
  `api/types/responses.rs:531,740`, `api/routes/files.rs:92-219`, etc.
- **If true, cost**: single-user server, so mostly UI jank/stalls during status
  refresh — but it also makes the batch endpoint's latency scale with subprocess
  count, and nothing documents which layer owns the blocking policy.
- **Investigation sketch**: count subprocess invocations for
  `GET /api/issues/status?issues=…` with N issues (trace `create_threads`);
  check tokio worker count vs. stall duration; decide boundary (make the git
  layer async-aware or wrap at handler edge consistently).
- **Confidence**: medium.

### H8 — Three hand-maintained API contracts (Rust ⇄ TS ⇄ OpenAPI) with no enforcement, and CI that can't catch cross-boundary breakage

- **Hypothesis**: response types are hand-mirrored in three places; nothing
  (codegen, runtime validation, contract tests, CI wiring) detects drift, so
  backend changes silently break the UI.
- **Signal**: `ui/src/api/issues.ts:18-60` / `repo.ts:8-20` hand-mirror
  `api/types/responses.rs` (e.g. `Issue`:79, `QCStatus`:137,
  `RepoInfoResponse`:579); no zod/valibot; fetchers cast `res.json()`
  unchecked; `openapi/openapi.yml` referenced by nothing (no codegen in
  `ui/package.json`, no utoipa in Cargo.toml) — maintained only by the
  `AGENTS.md` instruction; `ui-tests.yml` is path-filtered to `ui/**` so a
  backend contract change never runs the UI's tests; the Playwright suite mocks
  `/api/*` anyway (`ui/tests/helpers/routes.ts:124-140`).
- **If true, cost**: field renames/shape changes surface as undefined-props at
  runtime in front of scientists; the OpenAPI file rots into misinformation.
- **Investigation sketch**: field-by-field diff of 3-4 core types
  (`IssueStatusResponse`, `Issue`, `RepoInfoResponse`, `Checklist`) across the
  three definitions looking for existing drift; sketch one source of truth
  (generate TS from Rust via ts-rs/specta, or generate both from the OpenAPI).
- **Confidence**: medium-high that some drift already exists.

## 3. Questions for the maintainer

1. **[→H3]** `ghqc ui`/`serve` bind all interfaces (`0.0.0.0`/`[::]`,
   `src/api/server.rs:171-177`) with no auth, but `docs/serve.md` describes the
   URL as loopback. Is the wide bind required (e.g. does your Posit Workbench
   proxy setup connect from a non-loopback address?), or an accident?
   **Default**: treat as accidental exposure; review flags it and evaluates
   loopback-by-default.
2. **[→H3]** Are shared multi-user hosts (Posit Workbench) the *typical*
   deployment for `ghqc ui`, or do most users run it on personal machines?
   **Default**: shared hosts are common; severity is assessed under that
   assumption.
