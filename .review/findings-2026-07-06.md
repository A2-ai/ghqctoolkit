# Deep Architecture & Code Review — ghqctoolkit (0.7.1)

**Date:** 2026-07-06 · **Mode:** two-pass (addendum-driven) · Findings ranked by severity.

---

## 1. Architecture summary

`ghqc` is a QC-management system for scientific/pharma workflows that uses **GitHub Issues
as its system of record**: each QC'd file gets an Issue, QC lifecycle state (create → notify →
review → approve/unapprove → record → archive) is *serialized into* issue bodies/comments and
*re-parsed out* to reconstruct status. It is a hybrid — an interactive Rust CLI, an Axum HTTP
API, and an embedded React SPA — all sitting over a shared Rust core library and a git layer
(`src/git/`). ~33k LOC Rust, ~12.5k TS.

**Layering (intended vs. actual).** The intended shape is *CLI and API as peer frontends over a
shared core + git layer*. In practice both frontends carry their own orchestration and
validation, and `main.rs` is a third orchestration site — so the "single core" is real for
posting primitives (`post_with_blocking`, `batch_post_qc_entries`, `stash_review_file`) but
**not** for validation or for the approve/unapprove/rename orchestration, which the API
re-implements inline (Findings 4, 5, 8). The most load-bearing modules are `src/git/mod.rs`
(`GitInfo`, constructed on every path), `src/issue.rs` (`IssueThread`, the QC-state
reconstructor every flow depends on), and the `cli/context.rs ↔ api/routes/*` pair.

**Flows traced.** (1) *API approve* — `POST /api/issues/{n}/approve` → `approve_issue`
(`comments.rs:54`) parses the commit as bare hex, re-implements the blocking-QC gate inline,
posts the approval comment, then closes the issue with `.is_ok()`; it never calls the core
`approve_with_validation`. (2) *Status reconstruction* — `IssueThread::from_issue_comments`
folds comments in fetch order, matching literal grammar substrings to build the commit-status
map that `QCStatus` and every downstream report consume. (3) *Record generation* — client posts
an `output_path`, server writes the PDF there. Tracing these three is what surfaced the top
findings.

**Structural health.** The core abstractions are good (trait-generic, mockable git layer; a
real API test harness; a deliberately race-free config swap). The systemic weaknesses are all
at *boundaries*: the issue-body grammar is an unversioned string contract with ~7 writers and
≥2 drifted parsers; the CLI and API enforce different invariants for the same operations; and
the local server's trust boundary (unauthenticated, all-interfaces) does not match its
"loopback, single-user" self-image. For a tool whose product *is* the trustworthiness of the QC
record, the highest-value findings are the ones where state can be silently wrong (Findings 2,
3, 4, 5).

**Spot-check of the addendum map:** entry points (`main.rs:394`, `create_router`
`server.rs:43-132`), the all-interfaces binds (`server.rs:171-177`), the second issue-body
parser (`responses.rs:643-723`), and the auth crypto (`auth.rs`) all exist as described. No
map corrections needed.

**Priority-target dispositions:** **T1 CONFIRMED** (and understated — see F2, F7). **T2
CONFIRMED** (F4, F5, F8). **T3 CONFIRMED**, with a new **Critical** not in the survey (F1). **T4
CONFIRMED on facts but the rank is Medium**: the "~50 compensating closures" is really ~3–4 (the
rest are mandatory `JoinError`/hex-parse adapters) and the UI consumes the generic error string
opaquely, so the payoff is correct *status codes*, not a machine-readable field — see secondary
list. **T5 CONFIRMED**: real gix↔git-CLI behavioral divergences plus deep `ObjectId` leakage —
see F10. The survey's **H5 cache-merge worry is REFUTED**: `merge_file_changes` is sound (see
§5, What's good) — the real cache/diff bug is elsewhere (F3).

## 2. Primary findings (ranked)

### F1 — Unauthenticated arbitrary-path file write via `POST /api/record/generate` — **CRITICAL**
**Category:** D (trust boundary) / B · **Confidence:** High · **Verified in-session.**
**Evidence:** `src/api/routes/record.rs:245-259` — a client-supplied `output_path` is used
**verbatim** when absolute (`raw.is_absolute()` → `raw`) and joined without any `..` rejection
when relative; the server then `create_dir_all(parent)` and writes the PDF there. Contrast
`src/api/routes/archive.rs:34-74`, which for the *identical* request shape rejects `..`
components, canonicalizes, and enforces `canonical_parent.starts_with(repo_root)`. The guard was
known and simply omitted in `record.rs`.
**The issue:** Combined with F6 (server reachable from every interface, no auth), any other user
on the shared Posit Workbench host — or any network peer — can `POST {"output_path":
"/home/<owner>/.ssh/authorized_keys", ...}` (or `../../../etc/cron.d/x`) and create/overwrite any
file writable by the launching user, as that user.
**Blast radius:** Destructive overwrite of the owner's files (`~/.Rprofile`, `~/.bashrc`,
project data) and directory creation anywhere. The written bytes are a rendered PDF, not
attacker-controlled text, so clean code-injection RCE is not directly achievable — which is the
only reason this is not unqualified "Critical + RCE"; unauthenticated arbitrary create/overwrite
as another user on a shared host is Critical on its own.
**Remediation:** Mirror `archive.rs` exactly: reject `..`, join relatives onto the canonicalized
repo root, then canonicalize the parent and enforce `starts_with(repo_root)`. ~15 lines. **Effort:
hours.**

### F2 — Unanchored issue-body pattern matching forges or drops approval state — **HIGH**
**Category:** D / A · **Confidence:** High · **Verified in-session.**
**Evidence:** `src/issue.rs:390-396` (`parse_commit_from_pattern` = bare `body.find(pattern)`
over the whole comment, no line/quote/fence anchor), called at `issue.rs:339,346,361`;
unapproval is `comment.body.contains("# QC Un-Approval")` at `issue.rs:369`. The maintainer
confirms bodies/comments are hand-edited on GitHub and old-format issues are live.
**The issue:** The parser reads its control grammar *anywhere* in a comment. A GitHub "quote
reply" (`> approved qc commit: <sha>`), a `## File Difference` diff of a file that itself
contains the grammar, or a hand-typed note echoing it, all register as **real** approval /
review / unapproval events. Two concrete corruption paths verified by two independent passes:
- **Self-canceling unapproval:** `QCUnapprove` embeds the user's free-text `reason` verbatim
  (`approve.rs:73-75`). If the reason quotes `approved qc commit: <sha>`, the approval check
  (`issue.rs:346`) fires first and sets `approval_comment_index = index`; the unapproval check
  then requires `index > approval_index` (`issue.rs:371`) which is false for the same comment —
  so the comment meant to revoke approval instead **registers a fresh approval**, and status
  stays `Approved` even though `unapprove_with_impact` reopened the issue.
- **Silent gate vanish on hand-edit:** `parse_blocking_qcs` matches `### Gating QC` exactly
  (`issue.rs:448`). A hand-edited `### gating QC` / `###Gating QC` yields *zero* blocking
  entries — indistinguishable from "no gates" — so `all_approved()` passes and approval proceeds
  with the gate silently removed (`approve.rs:222-239`, same in `comments.rs:61-74`).
**Blast radius:** Wrong `QCStatus` on the Status tab, in the record PDF, and in the archive
(which reads `approved_commit()`), silently, for any issue whose thread quotes/echoes a control
phrase or whose gate heading was hand-touched. This is the QC record being wrong — the product.
**Remediation:** Introduce one `issue_grammar` module: line-anchor patterns to the `## Metadata`
block under the writer's `# QC *` heading (the review path already gates on the heading), skip
`>`-quoted and fenced lines, detect `# QC Un-Approval` only as the leading H1, and return an
explicit `ParseOutcome::{Parsed, Empty, Malformed}` so "couldn't read the gate" ≠ "no gate."
**Effort:** ~1 day for the anchoring fix; folds into the F7 unification.

### F3 — Excel diff silently reports "No differences" for changes outside a fixed window — **HIGH**
**Category:** F/D · **Confidence:** High · **Verified in-session.**
**Evidence:** `src/diff_utils.rs:158` (`rows_to_analyze = max_rows.min(20)`), `:183`
(`cols_to_check = max_cols.min(26)`), `:207` (`break` after 10 changed rows), feeding
`diff_excel_sheet` which returns `None` when `!has_changes` (`:120`) → `diff_excel_files` emits
the literal `"No differences between Excel file versions."` (`:78-83`).
**The issue:** If the only cell changes lie beyond row 20 / column 26 (or after the 10-row cap)
**and** the sheet's dimensions are unchanged, `row_changes` is empty, `has_changes` stays
`false`, and the tool reports the two files as identical. The text-diff path has no such cap;
only Excel does.
**Blast radius:** `file_diff` is what a scientist sees in QC notification comments
(`comment.rs:95`), review-vs-local diffs (`review.rs:114`), and relevant-file diffs
(`relevant_files.rs:214`). A real spreadsheet (>20 data rows is the norm) that changed in row 50
is presented as unchanged — the reviewer approves a file that actually changed. Directly attacks
QC trust.
**Remediation:** Track whether analysis was capped (rows>20, cols>26, or the break fired) and,
if so, never collapse to the "No differences" sentinel — emit an explicit "diff truncated;
additional changes not shown" marker so `has_changes` is set. Better: compute equality over the
full range independently before deciding "no differences." **Effort:** ~half day.

### F4 — API approve accepts commits absent from the branch; the "approval" is invisible to all downstream QC state — **HIGH**
**Category:** D / A · **Confidence:** High.
**Evidence:** `comments.rs:30-35,91,182-186` (`parse_str_as_commit` = hex decode only) vs
`cli/context.rs:641-651` (CLI requires the commit to exist in `issue_thread.commits`). Status
reconstruction attaches `Approved` only to commits found in the branch walk
(`issue.rs:212-227`); an unknown SHA never matches.
**The issue:** The API records `approved qc commit: <sha>` for a SHA the branch has never seen.
`approved_commit()` returns `None` (`issue.rs:302-306`), so `determine_status` on the now-closed
issue yields `ApprovalRequired`. The user was told the issue was approved; the system disagrees.
**Blast radius:** The record report prints "Approval required" (`record/mod.rs:314`); the
archive marks `approved: false` and archives the **latest** commit instead of the approved one
(`archive.rs:60-64`); blocking-QC gates treat it as unapproved and block dependents; the
comment's "file at approved commit" link 404s. The UI happens to only offer server-derived
commits, so today this needs a raw API/script call — but the API *is* the contract and nothing
server-side enforces membership.
**Remediation:** Move commit-membership resolution into the core (`resolve_thread_commit(&IssueThread,
&str) -> Result<ObjectId>`) and have `approve_issue`/`create_comment`/`review_issue` use it
(replacing the three CLI copies and the API hex-parse). **Effort:** ~0.5–1 day.

### F5 — API swallows `close_issue`/`open_issue` failure and reports success anyway — **HIGH**
**Category:** B / A · **Confidence:** High.
**Evidence:** core treats close/open as fatal — `git_info.close_issue(...).await?` (`approve.rs:245`),
`open_issue(...).await?` (`approve.rs:507`); the API discards it — `.await.is_ok()`
(`comments.rs:101` approve, `comments.rs:140` unapprove) and still returns **201 CREATED**.
**The issue:** On the API path the approval comment is posted first, then the close is attempted;
if the close fails (network blip, 5xx, rate-limit, permission) the failure is dropped, `closed`
becomes `false`, but the endpoint reports success. The result is an issue bearing a "QC Approved"
comment that is still **open** (or, symmetrically, an unapproved-but-still-closed issue). Status
logic never consults open/closed, so it reports `Approved`, disagreeing with GitHub's milestone
progress and with the CLI (whose interactive unapprove filters to closed issues and so cannot
even reach the stranded one). The UI receives `closed:false` but renders "Issue approved and
closed." unconditionally (`IssueDetailModal.tsx:1094`). Nobody is told. The core, written by the
same team, treats the identical call as fatal — this reads as an oversight, not policy.
**Blast radius:** Every API-driven approve/unapprove (the entire web UI Status/Record flow),
silent, accumulating.
**Remediation:** Have the API call the core `approve_with_validation`/`unapprove_with_impact`
(they already return the right errors) and surface partial success — return a typed
`{closed:bool}` and a non-201 (or explicit warning) when the close/open failed; UI warns on
`closed===false`. **Effort:** ~0.5 day; the core functions already exist and are tested.

### F6 — Unauthenticated API bound to all interfaces on shared multi-user hosts — **HIGH**
**Category:** D · **Confidence:** High · **Verified in-session.**
**Evidence:** `server.rs:171-177` binds `Ipv4Addr::UNSPECIFIED` / `Ipv6Addr::UNSPECIFIED` (all
interfaces); `--ipv4-only` only toggles family, never restricts to loopback; there is no
bind-address flag anywhere (`main.rs:1194-1234`, `ui/mod.rs`). No auth middleware in
`create_router` (`server.rs:43-132`). The printed URL and `docs/serve.md:25-26,82` say loopback,
so the exposure is invisible to operators. The maintainer confirms the original wide-bind
workaround is no longer required and shared hosts are the typical deployment.
**The issue / blast radius:** Every co-tenant (and, per network topology, remote hosts) can
drive GitHub writes as the owner (`comments.rs` comment/approve/close/unapprove), read arbitrary
repo files (`/api/files/{content,raw}`), and reach F1's file write — with zero credentials.
(Note: the path-traversal guards on `/api/files/*` and `/api/archive` are correct — see What's
good — so *read* traversal outside the repo is not possible; the exposure is the write in F1
plus authenticated-as-owner GitHub mutation.)
**Remediation:** Default the bind to `LOCALHOST`; add an explicit `--host`/`--bind` opt-in for
the rare legacy case; optionally embed a session token in the launched URL for defense-in-depth.
Wildcard CORS (`server.rs:35-37`) is intentional and out of scope. **Effort:** low (bind flip
trivial; token more work).

### F7 — Unversioned issue-body grammar with duplicated, drifted parsers — **HIGH (systemic)**
**Category:** A / D · **Confidence:** High.
**Evidence:** QC state round-trips through literal markdown with **no version marker** (writers:
`create.rs:39-40`, `comment.rs:24`, `approve.rs:32,73`, `review.rs:43,51`,
`relevant_files.rs:114-129`, plus `body_splitter.rs` re-emission). It is read by **two
independent semantic parsers** — the functional state machine in `issue.rs:329-606` and a
hand-reimplemented display parser in `responses.rs:643-723` — that ship in the *same* JSON
response and have already drifted:
- **Branch (confirmed):** `responses.rs:650-664` handles only markdown/plain links;
  `issue.rs:401-435` also handles HTML `<a>` (and HTML-link bodies are live — fixtures at
  `issue.rs:1561`). For an HTML-link body the display parser returns the raw
  `<a href=...>main</a>` string as the branch, so `issue.branch` (simple parser) and top-level
  `branch` (full parser) disagree in one payload.
- **Relevant-files (confirmed):** `issue.rs` requires `/issues/(\d+)` in the link regex
  (`issue.rs:22-23`); `responses.rs:670-671` accepts any `[x](y)`. A hand-edited gating link
  missing `/issues/` renders in the UI as a blocking QC but is **not** enforced at approval time.
**The issue / blast radius:** Renaming a section, adding a subsection, or tweaking a link format
requires synchronized edits across writers and both parsers with no compile-time linkage; the
two-parser split already produces UI-vs-enforcement disagreements. This is the structural root of
F2 and F4. (Note: `record/typst.rs` is a *third* markdown reimplementation but presentational —
it reads state from `IssueThread`, so it cannot drift on *state*; the survey's "third parser" is
refuted as a state parser.)
**Remediation:** Collapse to one shared grammar module (constants shared with writers; one
relevant-files tokenizer returning typed entries that both the UI list and the gate derive from);
optionally emit a `<!-- ghqc:v1 -->` marker at the single `CommentBody`/`body_splitter` chokepoint
to make future migrations detectable. The maintainer already endorses one shared parser.
**Effort:** ~3–5 days for the full unification (F2+F4+F7); the F2 anchoring subset is ~1 day.

### F8 — CLI and API are divergent re-implementations with no single enforcement boundary — **MEDIUM-HIGH (systemic)**
**Category:** A · **Confidence:** High.
**Evidence:** Approve/unapprove bypass the exported core entirely (`comments.rs:54-149` vs
`approve.rs:213,499`); rename orchestration and the `RenameComment` body are duplicated
near-verbatim (`cli/rename.rs:16-38,213-270` vs `issues.rs:412-434,441-511`); the blocking-QC
"approved" classification is encoded ≥3 times (`qc_status.rs:131`, `issues.rs:311-325`,
`comments.rs:188-221`); the default approval commit is computed three different ways
(`context.rs:582-593` vs `context.rs:650` vs `IssueDetailModal.tsx:842-848`) and has already
drifted. Validation lives in CLI constructors, in API handlers, and a third time in the UI.
**Concrete already-present drift:** (a) rename — CLI confirms only *detected* renames on *open*
issues; the API accepts any non-empty `new_path` on any issue state, so a closed/approved issue
can be retitled to an arbitrary path via the API, changing what future records/archives treat as
the QC'd file. (b) A latent outright bug: non-interactive CLI unapprove is unreachable — `find_issue`
returns only open issues (`context.rs:946-951`) but `QCUnapprove::from_args` then bails *if the
issue is closed* (`context.rs:740-745`, inverted), so `ghqc issue unapprove -m -f -r` can never
target an approved (closed) issue and will happily unapprove a never-approved one.
**Blast radius:** Change amplification on every future feature touching these ops (F4/F5 are
instances); three-way policy drift that is hard to even detect.
**Remediation:** Introduce core command functions (`approve`, `unapprove`, `comment`, `review`,
`confirm_rename`) that own all invariants and return typed results; make the API layer unable to
construct the request types without running core validation. **Effort:** 3–5 days incl. tests;
F5 + the unapprove bug are independently fixable in <1 day.

### F9 — Token store: master key stored adjacent to ciphertext; token files not permission-restricted — **MEDIUM-HIGH**
**Category:** D · **Confidence:** High · **Verified in-session (chmod gap).**
**Evidence:** The 32-byte AES-256-GCM master key is written to `root/master.key`
(`auth.rs:63-72`) in the parent of the ciphertext files `root/hosts/<b64>.enc`
(`auth.rs:85-88`), encrypted with nothing; the same key encrypts and decrypts (`auth.rs:100,165`).
`save_token` writes the `.enc` file and creates `hosts/` with **no** `set_user_only_permissions`
(`auth.rs:157-173`), unlike `master.key` (chmod'd at `:70`) and `root` (0700). The GCM nonce is
freshly random per save and the tag is verified on decrypt — the crypto core is correct; the
weakness is key management and file perms.
**The issue / blast radius:** On a shared host the confidentiality boundary is *only* the 0700 on
`root`; the encryption adds no defense-in-depth over plaintext + `chmod`, and the token files
themselves inherit the process umask. If the tree perms are ever relaxed (or read by root/backup
tooling), the token is trivially recoverable → GitHub account compromise.
**Remediation:** Derive/hold the key via an OS keyring (or at minimum document that security ==
filesystem perms), and call `set_user_only_permissions` on `hosts/` and each `.enc` file.
**Effort:** trivial for the chmod; moderate for keyring.

### F10 — gix ↔ git-CLI behavioral divergence and deep `ObjectId` leakage (migration risk) — **MEDIUM**
**Category:** A / E · **Confidence:** High.
**Evidence:** Several operations exist in both mechanisms and can disagree: remote resolution —
gix `find_default_remote` (`mod.rs:81`) honors the branch's configured remote / sole remote,
while the shell path hardcodes `"origin"` (`action.rs:149`), so a `git clone --origin upstream`
repo gets a different owner/repo/`remote_name` (which then poisons the upstream ref at
`status.rs:137`). Status builds the upstream as `remote/<same-branch-name>` (`status.rs:136-138`)
and ignores `branch.<x>.merge`, so a branch tracking a differently-named upstream is reported
fully "Ahead." HEAD is full-SHA via gix (`repository.rs:71`) but short via shell
(`status.rs:472`); the `DetachedHead` error is actually the unborn-branch case. `branch_tip`
(gix, local heads only, `file_ops.rs:145`) vs `branch_commits` (`git log`, full resolution)
makes the commit cache always-miss for non-local-head refs.
**The real cost — leakage:** `gix::ObjectId` is the de-facto commit-hash type across **26 files,
~200 non-test sites** — it is embedded in domain structs (`GitCommit.commit`, `GitStatus`,
`GitState`), in trait signatures (`GitCommitOps`/`GitFileOps`/`GitHelpers`), and used throughout
`issue.rs`, `create.rs`, `approve.rs`, `archive.rs`, the API types, and all of `cli/*`. Dropping
gix therefore isn't ~40 call sites; it's a wide type migration.
**Remediation:** Do the remote-resolution and upstream fixes first (they change behavior and gate
the migration), then introduce a project-owned `CommitId` newtype at the value-type chokepoints
(`GitCommit`/`GitStatus`/`GitState`) to contain the leakage before swapping the git backend.
Completing it also drops the `blocking-network-client`/curl/vendored-OpenSSL chain
(`Cargo.toml:7-15`). **Effort:** project-sized; the behavioral fixes are ~S–M each.

## 3. Also found (beyond the top 10)

Reported briefly to respect the 10-finding cap; several are genuinely Medium:

- **Coarse/wrong API error→HTTP status mapping (T4, Medium).** All seven `From` impls into
  `ApiError` stringify (`error.rs:64-115`); `IssueError::MilestoneNotFound`/`CommitNotParseable`
  → **500**, every `GitHubApiError` → **502** (incl. the *local* `CommentGenerationError` and
  auth `ClientCreation`), and the same upstream error yields 500 or 502 depending on nesting.
  Not-found and client errors look like server bugs, and React Query blindly retries the 500s
  against GitHub quota. Fix = one variant-preserving `IntoResponse` (fold in `classify_issue_error`);
  this deletes only ~3–4 genuinely-compensating handler closures (not the ~50 the survey
  estimated — the rest are mandatory `JoinError`/hex-parse adapters). ~1 day.
- **SSRF in the record image downloader (Medium).** `record/images.rs:75-107` passes
  issue-body-derived URLs straight to `ureq::get` with no scheme allow-list, no private/metadata-IP
  filtering, and default redirect-following; fetched bytes are embedded in the PDF. The 50 MB cap
  is fine and `file://` is not reachable. Add a scheme allow-list + resolve-then-reject
  private/loopback/link-local ranges + constrain redirects. ~1 day.
- **No graceful shutdown (Medium).** Neither `axum::serve` call uses `.with_graceful_shutdown`
  (`main.rs:1222`, `ui/mod.rs:70`); SIGTERM/Ctrl-C aborts in-flight GitHub writes and PDF renders.
- **Five blocking git/subprocess sites inline on tokio workers (Medium).** `commits.rs:63,86`,
  `fetch_helpers.rs:89,97`, `comments.rs:174` run synchronous gix/subprocess work without
  `spawn_blocking`, while ~11 neighboring handlers do wrap it — drift, not policy.
- **Config load recomposed at ~8 sites with real drift (Medium).** `Record` (`main.rs:800`) omits
  `load_checklists()` and `sitrep.rs:416` uses a different XDG fallback than `determine_config_dir`.
  *(Verified the `Record` omission is latent, not active: the record pipeline reads
  `options.checklist_display_name` and derives summaries from `analyze_issue_checklists(issue.body)`,
  never the `configuration.checklists` map — so today it's an inconsistency, not a wrong record.)*
  Extract one `Configuration::load(...)`.
- **`options.yaml` parse failure silently falls back to full defaults (Medium).**
  `configuration.rs:123-132` swallows a YAML typo with a `log::warn!` and reverts *all* options;
  distinguish "absent" from "present-but-unparseable."
- **Frontend phantom `CreateIssueResponse.issue_number` used as React key (Medium).** TS asserts
  the field (`create.ts:43-48`) but Rust never emits it (`responses.rs:412-431`); it becomes
  `key={undefined}` in `CreateResultModal` on batch create → duplicate-key collisions. Rust⇄TS
  drift is a real class here (also `previous_qc` response kind is dead, `Assignee.name`/
  `Milestone.state` type mismatches).

## 4. Low-hanging fruit

- `src/git/mod.rs:38-41` — `GitInfoError::RepoOpen`/`RemoteNotFound` use `#[error("...")]` with no
  `{0}`, dropping the wrapped gix cause from every message. Add `{0}`/`#[source]`.
- `src/cli/context.rs:627-629` — `QCApprove::from_args` bails with `bail!("")` on a closed issue →
  blank error to the user.
- `src/cli/context.rs:948-951` — `find_issue` matches issue titles by substring, so `--file main.R`
  can hit an issue titled `domain.R`. Anchor the match.
- `src/diff_utils.rs:518-527` — `format_hunk` header arithmetic produces `usize::MAX`-based line
  numbers for an all-insertion or all-deletion hunk (ugly output, no panic).
- `src/archive.rs:69,94` — `.expect("File to have file name")` panics on a filename-less path when
  `flatten` is set; entry names strip only a single leading `/`, no `..` check (low risk, git-tracked).
- `src/cli/cache.rs:167-172` — TTL description echoes the raw `GHQC_CACHE_TIMEOUT` string even when
  it fails to parse (effective TTL is 3600 but the CLI prints e.g. `"abcs"`). Show the effective value.
- `ui/src/api/checklists.ts:8-13` — `fetchChecklists` re-fetches the full `/api/configuration`
  payload uncached in an effect; read `checklists` off `useConfigurationStatus()` instead.
- `ui/src/api/assignees.ts:4-7` (`name: string` vs Rust `Option<String>`) and
  `ui/src/api/milestones.ts:7` (`'open'|'closed'` vs Rust can emit `"unknown"`) — widen the TS types.

## 5. Questions for maintainers

1. **Non-interactive `ghqc issue unapprove -m -f -r`** — is that path actually used, or is unapprove
   always interactive? The `from_args` state check is inverted (F8) so the args path is currently
   broken; whether that's live or effectively-dead code changes its severity.
2. **`POST /api/record/generate` absolute paths** — is accepting an absolute `output_path` ever
   intended (e.g. writing outside the repo on purpose), or should it always be repo-contained like
   `archive`? The fix in F1 assumes containment.
3. **Previous QC vs Gating QC in the UI** — the response parser collapses both to `blocking_qc`
   (`responses.rs:687-691`) so the UI's `previous_qc` branch is dead and they render identically.
